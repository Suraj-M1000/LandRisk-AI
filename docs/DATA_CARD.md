# LandRisk AI — Data Card (v1 draft)

> **Status:** draft. Items marked **[CONFIRM]** are proposed and not yet locked in `DECISIONS.md`.

## 1. Summary

The v1 dataset is **fully synthetic**. It is generated by `ml/generate_data.py` with a fixed random seed. It exists to demonstrate an end-to-end ML engineering pipeline (preprocessing → modelling → evaluation → explainability → Django). **Model performance on this data must never be presented as evidence of real-world predictive accuracy.**

## 2. Why synthetic

No open, labelled dataset of land-acquisition or infrastructure delays with the features this project needs was found. A real project-monitoring report (PAIMANA, `Projects_Report.csv`) was audited and set aside for v1:

- one row per project, with no time dimension (no snapshot history);
- no land-acquisition columns;
- `Revised Cost = 0` means "not recorded", and a blank `Revised Date` means "not revised / not reported";
- calendar effects dominate any date-based target (original commissioning year alone gave AUC ≈ 0.935; without calendar features ≈ 0.74).

The audit may later be used only to sanity-check ranges and base rates of the simulator. It is not part of the v1 training data.

## 3. Unit of observation

**One row = one infrastructure project, observed at one snapshot point in its life.**

- v1 uses **one snapshot per project**. The earlier three-snapshot design (early / mid / late) is deferred; a `stage` can be derived later from `months_elapsed / planned_duration_months`.
- Train/test splits are **by project** (trivially satisfied with one snapshot per project; the rule is kept for future multi-snapshot versions).

## 4. Schema (13 columns)

1) project_id : Unique identifier.
2) project_name : Realism only.
3) sector : Project category
4) state : Geographic context.
5) project_cost_cr : Project size or Project overall Finanical.
6) planned_duration_months : How many months the project was originally planned to take.
7) months_elapsed : How many months have already passed since the project started, at the moment we take our snapshot.
8) physical_progress_pct : How much of the actual project work has been completed?
9) expenditure_pct : Approximately what percentage of the project's planned/expected expenditure has been spent so far.
10) land_acquisition_required : Does this project require land acquisition?
11) land_acquisition_pct : How much this project require land acquisition? (in percent)
12) contractor_experience_years : Proxy for implementation capability

### Logical rules the data must satisfy

1. `land_acquisition_required = 0` ⇒ `land_acquisition_pct = 100` ("nothing left to acquire").
2. `0 ≤ physical_progress_pct ≤ 100`, `0 ≤ expenditure_pct ≤ 100`.
3. `1 ≤ months_elapsed ≤ planned_duration_months` **[CONFIRM]**. Snapshots are taken before the planned deadline so the task is *forecasting*, not detecting projects that are already overdue.
4. `project_id` is unique; no duplicate rows.
5. `project_name` values are clearly synthetic and must not imply real, named projects.

### Engineered features (computed in preprocessing, not stored)

`time_elapsed_pct`, `schedule_slippage = physical_progress_pct − time_elapsed_pct`, `spend_vs_progress = expenditure_pct − physical_progress_pct`, `land_gap = 100 − land_acquisition_pct`, `log_cost`.

## 5. Target definition

**[CONFIRM]** `delay_risk = 1` if the project's **eventual** delay exceeds 20% of its planned duration (the threshold is provisional; see `DECISIONS.md`), else `0`.

The simulator generates a hidden eventual delay from observable conditions **plus unobserved future events** (for example a late legal dispute or a monsoon season). The model sees only the snapshot features, so it cannot recover the label perfectly. This keeps the target future-looking and avoids a label that is a deterministic function of the inputs.

*Alternative considered:* `delay_risk = 1` meaning "currently shows risk characteristics". Rejected as the default because the label would then be a function of the features, and the model would only rediscover the generator's formula.

## 6. Generation approach

1. Draw project descriptors (sector, state, cost, planned duration) from uneven, right-skewed distributions, with sector-dependent duration and land requirement.
2. Draw `months_elapsed`, then physical progress, expenditure and land progress with realistic relationships (progress broadly tracks elapsed time, expenditure tends to run ahead of progress) and substantial noise, including exceptions in both directions.
3. Compute a hidden risk score from schedule slippage, spend-versus-progress gap, land gap, contractor experience and sector; add unobserved shocks.
4. Draw the eventual delay and label **probabilistically**, never with a hard cutoff.
5. Inject realism: a small share of missing values and outliers (rules documented here).
6. Validate with the sanity checks in section 8.

## 7. Known limitations

- The relationships are my assumptions, not measured facts about land acquisition in India.
- The land-acquisition-specific drivers named in SIH26017 (legal disputes, compensation, approvals, R&R) are only represented through `land_acquisition_pct` in v1.
- Contractor experience is a coarse proxy.
- A model can only be as realistic as the simulator; tests that check whether the model recovers the hidden weights are validation of the *pipeline*, not of reality.
- One snapshot per project means no real stage-wise or time-based evaluation in v1.

## 8. Sanity checks (to automate in `tests/`)

- no negative or out-of-range values;
- logical rules in section 4 hold for every row;
- delayed share is neither tiny nor near 50% **[CONFIRM target range]**;
- the same seed reproduces the same file;
- no feature is a deterministic function of the label.

## 9. Intended use

Learning, portfolio demonstration, and testing the Django ↔ ML integration. **Not** for real decisions, policy, or any claim about real project performance.
